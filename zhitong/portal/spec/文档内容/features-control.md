## 一句话

对送审计价表按规则检测疑似异常，可对照合同清单查超价超量；每条由您判定，决定留档可追溯。

## 适用场景

- 全过程造价咨询、跟踪审计中的进度款审核：每期送审前后排查一遍。
- 结算审核前的预检：在逐项审核之前先把可疑的清单项挑出来。
- 对照合同或中标清单，查哪些项单价、工程量超出合同，哪些是合同外新增。
- 继续上次没做完的复核：按记录查看还剩多少条待复核。

## 您可以这样说

::: utterances
- 对 2026-007 的送审计价表做一下投控检测。
- 用中标清单做基准，查一下送审里单价超合同、量超合同的项。
- 从置信高的开始，一次给我看 5 条。
- 第 1 条确认，和第 28 行重复列项了。
- 这一轮复核还剩多少条没看？
- 为什么这一条算大额？阈值是多少？
:::

## 需要准备的资料

| 资料 | 是否必需 | 要求 |
|---|---|---|
| 送审计价表 | 必需，可多份 | `.xlsx` / `.xlsm`，本期进度款或结算送审 |
| 合同 / 中标清单 | 可选 | 带单价的已标价清单，`.xlsx` / `.xlsm`。只有工程量、没有单价的招标工程量清单无法比对单价 |
| 项目编号 | 必需 | 例如 `2026-007`，进入每条异常的身份编号 |

送审与基准文件合计不超过 60 份、300 MB。

::: note
规则阈值来自随包的 `tk_detect.yaml`，版本 `v1-20260711`，状态为草案（draft），没有经过客户核对确认。阈值见本页「结果怎么读」。
:::

## 它会怎么做

::: steps
1. **读项目说明**（`read 项目说明.md`），找送审计价表和合同 / 中标清单。不明确时先预检（`probe.py probe`），把候选列给您确认。
2. **拉取文件**（`tos_pull`）。
3. **检测**（`tk.py detect`），工作目录 `工作/<日期>-投控/`。助手始终在项目根目录下用同一种相对路径写文件（如 `资料/4 结算资料/送审计价表.xlsx`），这样同一行清单在不同轮次的异常编号不变。
4. **汇报**：总条数与按规则分布 → 置信高的前若干条（带证据与原表位置）→ 与合同清单对不准的行 → 没跑的规则与原因 → 告警。
5. **逐条复核**。按严重度顺序，一次 3–5 条，给出证据和原表位置，必要时打开原表那一行。您判定后，助手追加一条决定（`tk.py review`），并告诉您还剩多少条（`tk.py progress`）。
6. **写待确认清单并推回桶**。每轮复核结束用 `tos_push` 推回。
:::

### 示例：2026-007 滨江综合办公楼（示例数据）

**第一轮：不带基准。**

您说："查一下这份结算送审的投控异常。"项目说明里没有登记合同或中标清单，助手只跑不需要基准的规则：

```text
tk.py detect --files "资料/4 结算资料/送审计价表.xlsx" --project-id 2026-007 \
  --out 工作/2026-10-19-投控/
```

助手汇报（节选）：

> 检测完成，共 290 条疑似：重复计取 2、暂估价 1、行内自洽 1、大额粗筛 286。大额粗筛置信最低，只按金额排序供抽查。
>
> 重点 4 条：
>
> 1. 重复计取｜综合脚手架（同文件同单位工程内同编码 2 行（金额非零的至少 2 行），送审金额 125,120.00，编码 011701001001，来源 送审计价表.xlsx·施工技术措施项目清单与计价表·第46行，置信度 0.7）
> 2. 重复计取｜综合脚手架（同文件同单位工程内同编码 2 行（金额非零的至少 2 行），送审金额 125,120.00，编码 011701001001，来源 送审计价表.xlsx·施工技术措施项目清单与计价表·第28行，置信度 0.7）
> 3. 整项存疑-暂估价｜钢质防火门（清单表「暂估价」列本行 50,568.00，送审金额 69,384.00，编码 010802003001，来源 送审计价表.xlsx·分部分项工程清单与计价表·第836行，置信度 0.6）
> 4. 整项存疑-自洽｜构造柱（量 96.4 × 单价 612.30 = 59,025.72，与送审金额 61,025.72 偏差 3.28%，编码 010502002001，来源 送审计价表.xlsx·分部分项工程清单与计价表·第374行，置信度 0.55）
>
> 没有合同或中标清单，单价超合同、量超合同、漏报、合同外新增 4 条规则本轮未跑（`baseline_not_provided`）。告警 1 条 info：按标题跳过 7 张非清单表。阈值 v1-20260711 仍是草案。
>
> 疑似不是结论。先看第 1 条，请您判定。

这 4 条与 [送审审定核对](/docs/features/check/) 的示例对得上：第 46 行综合脚手架在核对里是「仅送审」（审定删去），第 374 行构造柱在核对里带「送审计算错误」标记。

**逐条复核。**

助手用选项卡问："第 46 行 综合脚手架（重复计取，置信 0.7）：与第 28 行编码 011701001001、名称、特征、工程量相同，金额各 125,120.00 元。确认异常 / 判为误报 / 暂不判断？"您选"确认异常"，理由写"与第 28 行编码、名称、特征、工程量相同，重复列项"。

```text
tk.py review --result 工作/2026-10-19-投控/result.json --log 工作/2026-10-19-投控/复核.jsonl \
  --anomaly-id 3eb1778e-6da3-574a-bbab-aa16b02411ff --state confirmed \
  --reason "与第 28 行编码、名称、特征、工程量相同，重复列项" --reviewer 张工
```

助手回复："已记录到复核.jsonl。已确认 1、待复核 289；重点还剩 3 条待复核。第 28 行是同组的另一行，请您另行判定。"这一轮复核没有做完，助手写好待确认清单，等复核结束再推回桶。

**第二轮：带中标清单（假设）。**

如果您之后把中标单位的已标价清单放到 `资料/2 招标资料/中标清单.xlsx`，可以说"用中标清单做基准再跑一次"。结果写到新的工作目录：

```text
tk.py detect --files "资料/4 结算资料/送审计价表.xlsx" \
  --baseline-files "资料/2 招标资料/中标清单.xlsx" --project-id 2026-007 \
  --out 工作/2026-10-19-投控-2/
```

单价、工程量、漏报、合同外新增 4 条规则会运行。能严格对齐到合同清单的大额行改由这些规则判断，大额粗筛的条数随之减少。例如可能出现：

> 单价疑似超合同｜现浇构件钢筋（送审单价 5,128.60 > 合同单价 4,612.80，超 11.18%，疑似超出额 611,952.86，依据 中标清单.xlsx·分部分项工程清单与计价表·第742行 单价，编码 010515001002，来源 送审计价表.xlsx·分部分项工程清单与计价表·第768行，置信度 0.75）

疑似超出额由脚本按（送审单价 − 合同单价）× 送审量计算。是否成立仍由您判定，例如合同约定钢材按信息价调差时，可以判为误报并写明依据。

### 工作表「对不准的行」

只在给了合同 / 中标清单时有内容。示例第一轮没有基准，这张表为空。

### 复核.jsonl

每条决定一行，示例第一条：

```json
{"ts": "2026-10-19T06:42:18+00:00", "anomaly_id": "3eb1778e-6da3-574a-bbab-aa16b02411ff", "from_state": "pending", "hitl_state": "confirmed", "reason": "与第 28 行编码、名称、特征、工程量相同，重复列项", "reviewer": "张工", "anomaly": {"type": "duplicate", "anomaly_type": "重复计取", "item_code": "011701001001", "item_name": "综合脚手架", "source_file": "送审计价表.xlsx", "sheet": "施工技术措施项目清单与计价表", "row": 46, "line_amount": 125120.0, "excess_amount": null}}
```

- `hitl_state`：`confirmed` 确认异常；`dismissed` 判为误报；`pending` 撤回为待复核。
- 某条异常的当前状态 = 日志里它的最后一条决定；没有决定的是 `pending`。
- 改判就再追加一条，不删改旧行。时间 `ts` 是 UTC 时间。

## 结果怎么读

### 规则一览

| 规则 | 类别 | 需要基准 | 判定条件（草案阈值） | 置信度 |
|---|---|---|---|---|
| `duplicate` | 重复计取 | 否 | 同文件同单位工程内同一编码有 2 行及以上金额非零 | 0.7 |
| `code_repeat` | 编码重复（数据质量） | 否 | 同编码多行，但金额非零的不足 2 行；不判重复计取 | 0.3 |
| `zangu` | 整项存疑-暂估价 | 否 | 「暂估价」列本行非零，或名称、项目特征里有「暂估 / 暂定 / 暂列」；送审金额 ≥ 1,000 元 | 0.6；只在项目特征里出现裸词时 0.3 |
| `self_check` | 整项存疑-自洽 | 否 | \|量×价 − 合价\| ÷ 合价 > 2%，合价 ≥ 1,000 元 | 0.55 |
| `big_amount` | 整项存疑-大额 | 否 | 送审金额绝对值 ≥ 20,000 元；粗筛，置信最低 | 0.3 |
| `price_over_baseline` | 单价疑似超合同 | 是 | 送审单价 > 合同单价 ×（1 + 10%），合价 ≥ 1,000 元 | 0.75 |
| `qty_over_baseline` | 工程量疑似超合同 | 是 | 送审量 > 合同量 ×（1 + 15%），合价 ≥ 1,000 元 | 0.7 |
| `missing_submit` | 整项存疑-送审缺失 | 是 | 送审量、价、金额全空，合同清单该项金额 ≥ 10,000 元 | 0.5 |
| `new_item` | 合同外新增 | 是 | 合同 / 中标清单里没有对应项，送审金额 ≥ 5,000 元 | 0.55 |

- 疑似超出额：单价超合同 =（送审单价 − 合同单价）× 送审量；工程量超合同 =（送审量 − 合同量）× 送审单价。由脚本计算。
- 同一行被多条规则命中时只保留一条：大额与编码重复这两条粗筛规则让位于其他规则，其余按置信度高的保留。例如一行既过大额线又单价超合同，只列为单价疑似超合同。
- 对齐合同清单只认严格对齐：编码 + 名称 + 单位一致；补充码或无编码的行按名称 + 特征 + 单位。对不准的行不出金额，进入「对不准的行」。

### 置信档

| 置信档 | 含义 |
|---|---|
| 高 | 与合同清单严格对齐后判出的 |
| 中 | 重复计取、暂估价、行内自洽这类确定性规则 |
| 低 | 合同外新增、大额、编码重复，以及只在项目特征里出现「暂定」字样的暂估价 |

### 没跑的规则（`rules_skipped`）

| 原因 | 含义 |
|---|---|
| `baseline_not_provided` | 没有给合同 / 中标清单 |
| `baseline_invalid` | 给了合同 / 中标清单，但一行都没读出来 |
| `baseline_coverage_low` | 送审里带标准编码的行，严格对齐到合同清单的不到一半；本轮不判合同外新增（对不上的大多是基准没选全，不是真新增） |
| `rule_disabled` | 规则在阈值文件里关闭 |

### 什么时候能说"未检出异常"

只有送审表读出了有金额的清单行（`coverage.rows_parsed` 大于 0）且检出 0 条时，助手才会说"本轮未检出异常"。读不出清单行时，结果是 `insufficient`，不会说成没有异常。

## 需要您确认的事项

::: confirm
引擎只给疑似。每条是否构成问题、金额是否成立，都由您判定。助手不会替您判，也不会把"疑似"说成"存在"。

1. **每条异常的判定**：确认、误报或撤回为待复核，理由必填，写明依据（对照了哪份文件哪一行）。
2. **对不准的行**：编码相同但名称或单位不同，或合同清单里有多行可对。请指定对应的合同行，或判为不可比。
3. **没跑的规则**：没有基准时，超价超量、漏报、合同外新增都没有检查。
4. **error 级告警**：例如 `baseline_file_unparsed`（合同 / 中标清单没有解析出清单行）。
5. **阈值是否适用**：草案阈值不一定符合本项目的合同约定。需要调整时，由您明确提出，助手改用另一份阈值文件，并在汇报里说明用了哪份。
:::

## 限制与注意

- **阈值是草案**：`tk_detect.yaml` 版本 `v1-20260711`，客户侧状态 draft，不是行业标准阈值，也没有与客户核对确认。"金额完全相同的重复行会不会漏判"这一问题仍未有结论。
- **大额规则误报多**：大额是没有基准时的粗筛，置信度 0.3。示例项目不带基准时检出 286 条大额。建议先看置信高、中的条目。
- **身份编号依赖路径写法**：异常编号由项目编号、文件标识、工作表、行号算出。换了路径写法（相对路径改绝对路径）或换了文件，编号会变，旧的 `复核.jsonl` 就对不上。
- **重新检测写新目录**：换文件或口径后写到新的工作目录。助手可以按编号把旧目录里的复核结论带过来，但会说明哪些证据变了。
- **期次口径**：进度款表默认 `auto`；量和金额来自不同期次时（例如合同量 × 单价 ≠ 本期产值）不判行内自洽。
- **文件格式**：只读 `.xlsx` / `.xlsm`；`.xls` 需另存。送审文件里只有工程量、没有单价和金额的清单（疑似招标工程量清单）会被剔除，并给出 `file_unpriced` 告警。
- **模型不算钱**：疑似超出额和合计都由脚本给出，助手不自己计算。

## 常见问题

### 为什么有两百多条"大额"？

没有基准时，大额规则把送审金额 ≥ 20,000 元的行都列为疑似，这是粗筛，置信度最低。加上合同 / 中标清单后，能严格对齐的行会改由单价、工程量规则判断，大额条数会减少。

### 判错了能改吗？

能。对助手说"把第 3 条改回待复核"或"改成确认"，助手会追加一条新决定。`复核.jsonl` 只追加，当前状态以最后一条为准。

### 招标工程量清单能作基准吗？

不建议。单价超合同要比合同单价，漏报要看合同清单该项金额；只有工程量、没有单价的清单做不了这两项比对。请使用中标单位的已标价清单或合同清单。如果给的合同 / 中标清单一行都没有读出来，合同基准状态为 `invalid`，四条基准规则都不会运行，并给出 `baseline_file_unparsed` 告警。

### 为什么"合同外新增"这条规则没跑？

如果送审里带标准编码的行，严格对齐到合同清单的不到一半，本轮不判合同外新增，原因记为 `baseline_coverage_low`。多半是合同清单没选全，请补齐后重跑。

### 为什么这一条算大额？

助手会说明阈值来自 `tk_detect.yaml` 的哪个版本、门槛是多少（大额线 20,000 元）。这个阈值是草案。

### 下次打开还能接着复核吗？

能。复核记录在 `工作/<日期>-投控/复核.jsonl`，推回桶后，下次对助手说"接着复核上次的投控结果"，助手会先查进度，再从待复核的条目继续。
